How it was done

Both topologies were built in Linux network namespaces — real interfaces, real routing, real queueing — so the fault could be reproduced and measured rather than described.

The access switch held everything in one deep tail-drop queue, so voice waited behind bulk data in the same buffer. I replaced it with HTB class-based shaping, used u32 filters matching DSCP EF to steer RTP voice into a priority class, and bonded the two switch uplinks with 802.3ad LACP.

The captured before and after, unedited:

before rtt min/avg/max/mdev = 128.357/152.524/165.103/9.248 ms after rtt min/avg/max/mdev = 20.022/ 20.029/ 20.039/0.005 ms

Every mechanism maps one to one onto vendor configuration — HTB classes to a policy-map, u32 DSCP filters to match dscp ef, bonding to EtherChannel — so the work transfers to Cisco kit. The repository documents that mapping in full.

How it was done

The branch reached head office through a WireGuard site-to-site tunnel, with nftables enforcing policy at the branch edge. I confirmed the saturation against interface counters, then applied a time-based bandwidth policy that caps backup traffic inside business hours and releases it outside them.

Backup throughput was deliberately shaped from 20.7 Mbps to 1.31 Mbps during the day. The backup still finishes; it just stops competing with the people trying to work.

What the user reportsWhat the obvious check says

How it was done

Forest, DNS, DHCP, the OU tree, the group model, policies and delegation are all created by idempotent PowerShell. There is no click-through in the build and no screenshot of a wizard in the repository — a domain that exists only as remembered clicks cannot be rebuilt under pressure.

Test-DomainHealth.ps1 answers 25 questions about the domain with pass, warn or fail and exits non-zero on any failure. It exists because the failures that cost the most time are the silent ones: a missing reverse zone, an unauthorised DHCP server, a share that never came back after a reboot. None of those announce themselves.

Helpdesk password-reset rights are delegated with dsacls as three explicit permissions on one subtree, rather than by adding people to Account Operators and handing them the whole directory.

The build scripts and the fault injection are written and checked by CI on every push. Measured evidence is committed after the first full run — no figures are published here before they exist.

How it was done

A problem must persist across three checks before the tool raises anything, and recovery across five before it stands down. The asymmetry is deliberate: it should be harder to convince the system a fault is over than that it started. Alarms fire on changes only, so a long outage produces two lines instead of two hundred.

Being testable drove the design rather than following it. Probes never raise — an unreachable host is just data. The alarm logic holds no clock and does no input or output, which is why twenty minutes of behaviour can be exercised in a millisecond.

It exits non-zero when something is wrong, so it works as a check after a change, not only as a dashboard.

A test found a real bug: the configuration silently ignored unknown settings, so a typo would be dropped without a word and the limit never applied. The tool would run, look healthy, and never fire. Unknown settings are now an error at startup that lists the valid ones.

How it was done

Courses that check answers by comparing text teach people to produce the expected words, not working code. Marking properly normally needs a server to run submissions, which means hosting, cost, and an account before a learner writes a line.

This runs Python in the browser through Pyodide, compiled to WebAssembly, and marks each submission against a hidden test suite. Course content is data, separate from the engine, so adding material needs no code changes. Around 900 lines of plain JavaScript, no framework.

A rendering pipeline kept taking the whole machine down. I made it check itself before it runs.

Batch image pipeline, one graphics card, 12 GB of memory

How it was done

Two jobs overlapping meant an out-of-memory failure that froze the machine, and bad output from an early stage wasted time on every stage after it.

A preflight check validates the environment, confirms the models are present and checks free memory before anything is submitted, and jobs are scheduled one at a time so stages never overlap. A quality gate scores each stage's output and rejects failures before they reach the next one.

One of the quality measures was built, tested against known inputs, found unable to separate the cases it was meant to catch, and removed rather than shipped as a check that fires on everything. Knowing when not to ship something is the part of this work I am most confident about.
