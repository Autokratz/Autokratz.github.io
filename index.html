Case study 01

Protecting voice inside a saturated uplink

Campus LAN · QoS classification + 802.3ad link aggregation · Linux network namespaces

Problem
A head-office campus LAN carried VoIP and bulk data over the same 10 Mbps access-layer uplink. Whenever a bulk transfer ran, the uplink filled and voice quality collapsed — round-trip time rose to an average of 152 ms with swings up to 165 ms, and calls started dropping packets. The access switch was holding traffic in a single deep tail-drop queue, so voice waited behind bulk data in the same buffer.
Approach
I built the topology for real rather than simulating it — two access hosts (a VoIP phone and a data workstation), an access switch and a core switch, each in its own Linux network namespace with real routing and real queueing. I reproduced the fault first, measured it, then rebuilt the egress path: HTB class-based shaping replacing the tail-drop queue, u32 filters matching DSCP EF to steer RTP voice into a priority class, and the two switch uplinks bonded with 802.3ad LACP.
Result
Voice RTT dropped to a flat 20 ms and jitter fell to effectively zero, with voice packet loss eliminated entirely. The important part is what didn't change: the uplink still runs at about 99% utilisation. Bulk traffic was never throttled — average throughput actually rose slightly. The link is just as full; voice simply no longer waits in the same queue.

Case study 02

Recovering a WAN link at 100% saturation

Remote branch · WireGuard site-to-site VPN + time-based bandwidth policy

Problem
A remote branch reached head office through a site-to-site VPN over a 20 Mbps WAN link. An unscheduled NAS backup ran during business hours and pushed the tunnel to 100.1% of link capacity. Interactive traffic became unusable: round-trip time averaged 713 ms with peaks past 1.2 seconds, and 3.33% of packets never arrived at all.
Approach
I built the branch topology — NAS, workstation, branch router, WAN segment, HQ router and cloud server — again in network namespaces, with a real WireGuard tunnel carrying the traffic and nftables enforcing policy at the branch edge. I confirmed the saturation against interface counters, then applied a time-based bandwidth policy that caps backup traffic to a small share of the link inside business hours and releases it outside them.
Result
Output utilisation fell from 100.1% to 5.2%, branch RTT from 713 ms to a stable 30 ms, and packet loss to zero. Backup throughput was deliberately shaped from 20.7 Mbps down to 1.31 Mbps during business hours — the backup still completes, it just no longer competes with the people trying to work.

Case study 03 In progress

A domain that builds itself, then breaks on purpose

Windows Server 2022 · Active Directory · PowerShell · fault injection

Problem
Most Active Directory labs demonstrate that a domain can be stood up. That isn't a difficult claim and it isn't worth much, because the wizard does the work. A domain that exists only as a sequence of remembered clicks can't be rebuilt under pressure, and the person who built it becomes the single point of failure.
Approach
I built a 32-user fictional freight company — forest, DNS, DHCP, OU tree, group model, policies, delegation — entirely from idempotent PowerShell. No click-through, and no screenshot of a wizard anywhere in the repository. Then two things most labs skip: a health check that answers 25 questions about the domain with PASS, WARN or FAIL and exits non-zero on any failure, and a fault injector that deliberately breaks the domain three times so the diagnosis is documented rather than assumed.
Result
Every fault was chosen because the symptom the user reports points nowhere near the cause, and the obvious first check comes back completely clean. That table below is the point of the whole project — the habit worth building is that a clean obvious check narrows a problem, it does not close it.
What the user saysThe obvious check saidWhere the answer actually was
"My desktop settings disappeared" GPO linked and enabled Security filtering removed Read for Authenticated Users, so the computer couldn't evaluate the policy at all. GPMC looks normal.
"It keeps locking me out and I'm not even logged in" Account locked; password reset changed nothing A stale background credential retrying. Event 4740 names the source workstation. Unlocking first just restarts the loop.
"Nobody at the site can log in" DC up, console browsing the web fine The DC's own resolver was pointed at public DNS. SRV records stopped resolving — outbound browsing worked because of the fault.

Status: the build scripts, the health check and the fault injection are written. Captured evidence is committed after the first full run — no figures are published here before they're measured.

Case study 04

netwatch — alerting that doesn't cry wolf

Python package · 118 tests · mypy strict · CI on three versions

Problem
Monitoring tools either want a server, a database and a dashboard, or they are a ping in a while loop that nobody can act on. And the naive version of either has the same flaw: it alerts on the first breached sample and clears on the first good one. Against a genuinely flapping link that produces an alert and a recovery every interval — and a channel that cries wolf gets muted, which turns your monitoring into an outage you hear about from a user.
Approach
A dependency-free package with hysteresis at its centre: a breach must persist for three consecutive evaluations before firing, and recovery for five before resolving. The asymmetry is deliberate — it should be harder to convince the system a fault is over than that it started. Events fire on transitions only, so a long incident produces two lines, not two hundred.
Result
Testability drove the architecture rather than following it. Probes sit behind a Protocol and never raise, so an unreachable host is just data. The alert engine holds no clock and does no I/O, which is why twenty minutes of hysteresis is exercised in a millisecond. A non-zero exit code makes it usable as a post-change gate, not only a dashboard.

Case study 05

NEURON — running real Python in the browser

Learning platform · Pyodide / WebAssembly · no backend

Problem
Coding tutorials that check answers by matching strings teach people to produce the expected text, not working code. Anything that grades properly normally needs a server to execute submissions — which means hosting, cost and an account before a learner can write a single line.
Approach
I built the whole platform client-side. Python runs in the browser through Pyodide compiled to WebAssembly, and each quest carries a hidden assert-based test suite that runs against the learner's actual submission. Course content is declarative data, separate from the execution and grading engine, so adding material takes no code changes. Progress, XP and skill-tree unlocks persist in localStorage.
Result
52 graded quests across a skill-tree progression with boss challenges, in roughly 900 lines of vanilla JavaScript, HTML and CSS. No framework, no backend, no account, no hosting bill — it is a static page that grades real code.

Case study 06

Keeping a single GPU from falling over

Batch inference orchestration · automated quality gating · 12 GB VRAM ceiling

Problem
A multi-stage inference pipeline — detection, enhancement, upscaling — had to run on one consumer GPU with 12 GB of VRAM. Two jobs overlapping meant an out-of-memory failure that took the whole machine down, and bad output from an early stage wasted GPU time on every stage after it.
Approach
I wrote a preflight health check in Bash that validates the environment, confirms model availability and checks VRAM headroom before anything is submitted, and enforced single-job scheduling so stages never overlap. A Python quality-control gate scores each stage's output against defined thresholds and rejects failures before they reach the next stage. Pipeline configuration lives in a versioned recipe file, with the operational runbook kept under Git alongside it.
Result
Out-of-memory crashes stopped. Failed output is caught at the stage that produced it rather than after three more stages of wasted compute, and any run can be reproduced from its recipe.
